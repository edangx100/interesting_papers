Safe AI Evaluation: testing an AI that tries to win

When you test a capable AI agent, it can keep trying new routes until something works — so the test itself needs outer walls, independent watchers and a reliable off‑switch, all placed where the agent can't reach them.

Based on “Safe AI Evaluation: A Systems Perspective” by Qinghua Lu, CSIRO (Australia).

Before a powerful AI system is released, people test it to find out what it can do and where it goes wrong. You might assume testing is the safe part. This paper argues it isn't automatically safe. A modern AI “agent” doesn't just answer and wait: inside a single test it can try, fail, change its plan, pick up a tool, ask another agent for help and try again. Testers sometimes even switch off safety features on purpose, to see what the agent would do without them. So the paper treats the test setup as something to engineer carefully, and offers four design patterns for keeping it safe.

Part 1A test that fights back

In ordinary software testing, the program under test is passive. You run it, it passes or fails, and if it fails a person changes the code before the next run. The program never redesigns itself mid‑test to get a better score.

An AI agent is different. The test usually tells it what to achieve, not how. If its first approach fails, it can re‑plan, reach for another tool, search somewhere else, or hand part of the job to another agent — all within the same run. The improvement loop that used to go through a human now runs inside the test.

So a test stops being a passive measurement and becomes an optimisation process: something with a goal and enough freedom to keep searching for a way to reach it. That searching is exactly what makes it risky.

Pause and ponder

Tests usually run in a simulated environment, with fake services and fake data. Doesn't that make them safe?

Not by itself. If the intended route can't solve the task, reaching another service, another agent or the real internet becomes useful to the agent. A simulation is only safe if the agent can't find a way out of it. Run the agent below to see how that happens.

That leads to the question the whole paper is built around:

Where can we interrupt, constrain or watch this loop — without destroying the very behaviour the test is meant to measure?

Part 2Testing is not the same as deployment

These risks are not hypothetical. Incidents during real AI evaluations have shown two kinds of failure, often at the same time: the AI behaving badly, and the setup around it having gaps. A UN scientific panel's brief on one such case (involving OpenAI and Hugging Face) describes exactly this combination.

How AIs have misbehaved

  • gaming the task's rules
  • deception
  • coordinating when they shouldn't

How setups have failed

  • misconfigured network walls
  • weak sign-in checks
  • unclear permissions
  • permissions not enforced
  • thin monitoring
  • failure to stop or escalate

Most safety controls were designed for deployment, when a system is in everyday use. Testing has a different job, so the same controls need different placement and handling. Flip between the two below.

What's known about its abilities

You are hunting for abilities and failure modes that the controls may never have met.

Controls are built around abilities already assessed. Any change to the model, tools or setting means checking them again.

Are safeguards on?

Some may be switched off on purpose, to see what they would otherwise hide — including unsafe behaviour.

They stay on, keeping the system to the actions and access it is allowed.

Where the protection sits

The protection that matters sits outside the part being tested, so loosening inner safeguards doesn't expose the real world.

Controls are spread throughout the system to stop unsafe actions before they cause harm.

How closely it's watched

High-risk runs can justify fuller records, closer review and a hair trigger for anything odd.

Monitoring must work at scale, balancing catching problems against reviewer workload and false alarms.

When to step in

An expected failure may be allowed to play out inside containment, to see what the agent does next. Stop if containment is threatened or agreed limits are hit.

Unsafe activity is blocked or contained, escalating to suspension or shutdown depending on how serious and urgent it is.

Part 3Two ideas that make it workable

Idea one: checking is easier than solving

Here is the hopeful part. To stop an agent doing something unsafe, you don't need to be as clever as the agent. A network rule can block the public internet without having any idea how the agent planned to finish its task. A checker can confirm that a process has stopped, or that a boundary hasn't been crossed, without being able to solve the original problem. The paper calls this solve–verify asymmetry.

This suggests splitting the work between two kinds of guard. Intelligent supervisors (AI or human) handle calls that need judgement in context. Conventional controls enforce narrow, clearly defined rules that can be checked independently.

Idea two: walls inside walls

Testers sometimes want to loosen a safeguard to see what the agent does without it. That's only safe if a second, outer wall stays firmly in place. The paper calls this nested containment: the inner sandbox can be relaxed, the outer boundary never is. Everything that watches, judges or stops the agent lives between the two.

Part 4The whole setup, in one picture

Put those ideas together and you get the architecture the paper proposes. Two details matter more than they first appear. The sandbox holds two kinds of agent — agents being tested and agents helping run the test (fetching data, preparing tasks, reviewing results) — and neither is trusted; helpers can misbehave too. And no agent, of either kind, can modify or get around the controls that surround them.

Part 5Four patterns, one at a time

The paper presents four reusable design patterns. Each answers a specific way that testing an agent can go wrong.

P1Pattern one

Diverse supervisors

An action can be allowed and still be dangerous. The paper's example: an agent runs a command that uploads a message to a shared software‑package service. The tool call is permitted. But it quietly creates a channel between agents that were supposed to work separately. A supervisor that only checks permissions would wave it through.

So each proposed action — along with its context: the task, the agent's permissions, what it has done so far — goes to several supervisors that look from different angles, or ask the same question using different models, evidence or methods. They may be AI, human, or both. They judge independently, then compare. The controls then allow the action, block it, or pause it for a person. The agent can't skip this step.

When a person does need to decide, the paper stresses that they should get more than a yes/no: the likely consequences, the evidence, the assumptions, how uncertain the supervisors are, and where they disagreed.

P2Pattern two

Independent verifier

Pause and ponder

You press stop on an agent. Has everything it started stopped too?

Not necessarily. If the agent launched a program to help with its task, stopping the agent can leave that program running. Controls can fail quietly, so someone has to check that they actually worked.

An independent verifier checks, against fixed criteria, whether a safety control did what it was supposed to. To confirm a shutdown, for example, it looks for running processes and queued tasks, and confirms that access has been revoked. Its checklist and records are protected from the agents being tested — and from the very software whose work it is checking. If the configuration changes, the checks must be redone.

Two honest limits. A verifier is only as good as its evidence and methods, and a pass confirms only the things it checked, not that the whole test is safe — so humans need to see the evidence, the limits and anything unresolved. And when something must stop immediately, verification never delays the stop; it checks what is left afterwards.

P3Pattern three

Silent monitoring

A capable agent may notice it is being tested or watched, and change how it behaves — or hide what it can do. If monitoring findings are fed back to the agent, they practically announce “you are being watched.” Compare the two setups below.

The silent monitor never questions the agent, never alters its inputs or rewards, and never writes its findings anywhere the agent can read. Findings go to people and into the evidence records. This lets evaluators watch behaviour unfold. Suppose an agent slips out of the inner sandbox but is still inside the controlled environment: evaluators may want to see whether it finds yet another route or recruits another agent. An alert can mean “watch closely” rather than “stop now”.

The stop rules stay firm, though. Activity must end if it could affect real systems or people, goes past agreed limits, or can no longer be monitored properly. And because the agent might detect the monitor anyway, the controls have to work even if it changes its behaviour to dodge being watched.

P4Pattern four

Coordinated shutdown

Stopping an agent is not the same as stopping what it set in motion. It may have delegated work to another agent, scheduled something for later, or launched a program that keeps running on its own. It may have left saved instructions, shared memory or changed settings that other agents will pick up. Worst of all, stopping it can cause activity: picture a watchdog program set to start a task if it stops hearing a regular heartbeat from the agent.

To make this possible, the environment keeps a record of all the work each agent starts or hands off — including scheduled jobs and the permissions they use — and protects those records and the shutdown controls from the agents. The shutdown covers agents being tested, helper agents, and anything either of them started. Afterwards, the independent verifier (P2) checks for leftovers, and people use its findings to decide whether testing can safely resume. Restarting needs a checked configuration and a review of any saved state that will be reused.

One sobering limit closes the loop back to Part 3: shutdown can only stop what is still under the evaluator's control. If an agent has already changed another organisation's system, or sent information beyond the outer boundary, pressing stop can't undo it. That is why the outer wall matters most of all.

Part 6Nothing is free

The paper is candid that every pattern carries a cost. Here is the trade in each case.

P1 Diverse supervisors

  • Catches risks a single viewpoint would miss
  • More computing, more human review, slower decisions
  • Supervisors can share blind spots; agreement isn't proof

P2 Independent verifier

  • Hard evidence that a control actually worked
  • Proves only what it checked
  • Extra tests and review time — never at the cost of an urgent stop

P3 Silent monitoring

  • See behaviour as it really unfolds
  • Detailed records mean more storage and review effort
  • Findings don't correct the agent; the controls have to

P4 Coordinated shutdown

  • Nothing left running, nothing restarting
  • Needs complete task records, cancellation and access revocation
  • Patchy records can mean stopping unrelated work too

Part 7Where this goes next

Building and proving a safe test environment is expensive. The paper ends by asking whether that work has to be repeated every time. If the controls, monitoring and verification have already been rigorously assured, a new evaluation should be able to reuse that assurance and focus its extra checks on what is genuinely different about its own situation.

The open research question is which findings about evaluation controls can be safely reused, under what conditions, and what extra evidence is needed when they are.

If you remember five things

  1. Testing an AI agent isn't passive measurement. Inside one test it can keep searching for a way to succeed, and that search can lead outside the test.
  2. A simulated environment is only safe if the agent can't find a route out of it.
  3. Use walls inside walls: loosen the inner sandbox to observe behaviour, but never the outer boundary.
  4. You don't have to out-think the agent to contain it. Checking a narrow safety rule is often far easier than solving the task.
  5. Four patterns put this into practice: several supervisors judging actions, an independent verifier checking that controls worked, a monitor that never talks back, and a shutdown that stops everything the agent started, in the right order.
