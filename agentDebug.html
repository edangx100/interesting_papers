Where AI agents go wrong

Most agent failures trace back to a single early mistake. Find that one step, tell the agent what happened, and let it run again from there: it succeeds far more often.

An explainer of Where LLM Agents Fail and How They Can Learn From Failures by Kunlun Zhu and colleagues at UIUC, OpenManus, AMD and Stanford (arXiv:2509.25370, September 2025).

An AI agent is a language model given a job and a set of steps to do it in. It looks at what is in front of it, decides on one move, makes the move, sees what happened, and goes round again. Buying a shirt on a shopping site, tidying a virtual kitchen, answering a question that needs three web searches: all of these are dozens of small decisions in a row.

When a run like that fails, the obvious place to look is the end, where things visibly fell apart. This paper's argument is that the end is almost never the cause. One step early on goes quietly wrong, the agent carries that mistake forward as if it were true, and every later decision is built on it. The authors read through more than 500 failed runs by hand to check, and this pattern is what they kept finding.

So they did three things: named the ways a step can break, hand-labelled 200 failures using those names, and built a tool that reads a failed run, points at the one step that mattered, and hands the agent a note before it tries again.

One step, four small jobs

To talk about where a step breaks, you first need the parts of a step. The authors split every decision into four jobs, done in order.

Failure travels forward

Because each job feeds the next, and each step feeds the next step, a small wrong belief has a long life. An agent that misremembers what is in a cupboard will plan around a cupboard that does not exist, then read the resulting non-events as bad luck, then plan around those.

Memory and reflection are the quiet ones. They rarely look like errors at the time, they usually happen five to fifteen steps in, and they are the most likely to cascade. A malformed action is loud and often survivable. A misremembered fact is silent and usually fatal.

Laid out side by side, failed runs make the pattern visible: a first bad step somewhere in the middle, then a widening stain.

Five places a step can break

The hand analysis produced a vocabulary: seventeen named failure modes, sorted into the four jobs of a step plus a fifth bucket for problems that are not the agent's fault at all. The point of naming them is that a name can be pointed at. "Something went wrong around step 6" is not actionable. "At step 6 you planned around an object you never saw" is.

Two hundred failures, labelled by hand

A vocabulary is only useful if someone has applied it carefully to real runs. Ten graduate annotators went through 200 failed runs step by step, tagging each of the four jobs at each step. The instruction that makes this dataset unusual: do not flag every mistake you see. Flag the smallest set that explains the rest.

Finding the one step that mattered

Their tool, AgentDebug, reads a failed run and works in three passes. First it goes over every step and asks, for each of the four jobs, whether it matches one of the seventeen named modes. That gives a map of everything that went wrong, which is usually a lot.

Then it picks one: the earliest point at which the run became unrecoverable. Not the first blemish, and not the loudest one. The test is counterfactual. Had this step gone right, could the run have succeeded?

Finally it writes the agent a note naming that step, that job and that failure mode, and restarts the run from exactly there rather than from the beginning. Five attempts at most. If an attempt still fails, the note gets sharper.

What changed

Two questions, measured separately. Can it find the right step? And does finding it actually help?

On finding it, the bar was low. Asking a model outright to name the faulty step got the exact step 28% of the time, and got step, job and failure mode all correct in well under one case in a hundred. Working through the run step by step, or halving it repeatedly, did worse. AgentDebug got the step right 45% of the time and all three right in 24% of cases.

On whether it helps: in the simulated-house tasks, every backbone model improved, and the weakest improved most. A small model that solved 21 tasks on its first attempt solved 55 with debugging. Across all three settings the gain reaches 26% relative to the starting score. The comparison was held to the same total token budget as the alternatives, so this is not simply the result of letting the agent think for longer.

What this doesn't settle

The debugger is itself a language model reading a transcript, and it turns out to be a demanding job. Swap the strong model behind it for a weaker one and the diagnosis mostly collapses, which puts a floor under how cheap this can get.

  • Three benchmarks, all text-based and all simulated. Nothing here covers long-running, multimodal or high-stakes work, and the authors say so.
  • Agreement between human annotators was moderate rather than high, which is honest but also a reminder that "the root cause" is partly a judgement call.
  • The description of the second stage is not quite consistent inside the paper: the prose describes testing corrected actions to see whether the run would have succeeded, while the accompanying procedure notes that the stage runs as a single model judgement with no re-execution.
  • The debugger reads a transcript that already labels each step's four jobs. Agents that do not narrate themselves this way would need that structure added before any of this applies.

What survives all of that is the central habit, which is cheap to adopt and does not need their code: when an agent fails, stop reading the end of the transcript. Look for the first step where it started believing something untrue, and start again from there.
