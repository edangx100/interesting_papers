Harness² explained

Harness2

An AI agent that rewrites its own toolkit in the middle of a task, judges each change by watching how its behavior shifts, and keeps notes so it gets better at improving itself with every new job.

A visual guide to “Harness2: Recursive Agent Harnessing for an Open World” by Ruiyao Xu, Yanfei Chen and colleagues at Google Cloud AI Research and Northwestern University, October 2026.

Hand the same AI model a different set of instructions, tools and checklists, and it can go from mediocre to excellent. That surrounding kit is called a harness. People usually tune harnesses by hand, and automatic tuning usually needs an answer key to score each attempt. Real work rarely comes with one. This paper shows how an agent can improve its harness while it works on an unfamiliar task, with no answer key, and how it can save the lessons from each round of improvement so the next round goes better.

An agent is a model wearing a harness

Think of the model as a capable new hire, and the harness as everything the company hands them on day one: a role description, house rules, a notebook, playbooks, tools with instructions, and colleagues to delegate to. In this paper the model’s internal weights never change. Only the harness does.

Harness² splits the harness into eight parts, and each part is a plain file the system is allowed to rewrite. Tap any part to see what it does.

Why this is hard in the open world

Earlier systems tuned a harness ahead of time against practice tasks with known answers, then froze it and shipped it. The trouble is that real work keeps changing. The authors call this setting the open world: new tasks keep arriving, each with its own requirements. They name two obstacles.

Their way out is to notice that the process of improving carries over even when the fixes don’t. How a weakness gets diagnosed, which changes get tried, and what those changes reveal are useful on the next task too. So the paper asks:

Can self-improvement upgrade both the harness in hand and the way future harnesses get upgraded?

One step: propose, probe, compose

Without an answer key, how can the agent tell whether an edit helped? Harness² borrows the logic of a careful experiment: change something, rerun under identical conditions, and look at what behaves differently. Step through it below.

It’s a bit like tasting two versions of a soup side by side. You don’t need a judge’s scorecard to notice that one version finally has enough salt, or that the other scorched on the bottom.

The authors are careful about what this evidence is worth. A contrast tells you how behavior changed, not whether the final answer is correct. Runs are noisy, and the editor and the agent may share the same blind spots. So contrasts guide the composer’s choices rather than serving as a grade.

Spending more effort: wider or deeper

One step can be scaled up with a budget, written k. There are two shapes. Parallel recursion explores k ideas at once and lets several composers each draw on the whole pile of evidence. Sequential recursion chains k steps, each building on the last. Either way, when there’s more than one finished result, a selector compares the outputs without knowing which harness produced which, and picks one.

Both shapes kept improving as the budget grew. With Gemini 3.5 Flash on WorkBuddy-Bench, going from k = 1 to k = 5 in parallel lifted the coding score from 76.5 to 80.8, and the office score from 79.5 to 83.4. At just k = 2, either shape already beat every comparison method run at k = 5, and parallel finished a little ahead at the top of the range.

The comparison matters because extra effort alone isn’t enough. A rival method that also spends more compute per task, Harness Scaling, actually slipped between k = 2 and 3, and a memory-based method, ReasoningBank, bounced around. What helped was spending the effort on structured, evidence-backed revision.

The second loop: getting better at getting better

Everything so far happens inside a single task. The outer loop is the recursion in the title: a harness whose job is improving harnesses. The paper calls it the continual improvement harness, ℛ. At its heart is a library. After each task, Harness² looks back over the whole improvement record, pulls out lessons that the runs actually support, and files them away.

ℛt+1 = Update( ℛt , ℋ★t , 𝒟t )

Read it as: the improver for the next task equals the current improver, updated with the harness this task adopted (ℋ★) and the full record of how it got there (𝒟). Each library entry holds a working harness plus a notes file describing when it applies, what was learned, and the evidence. Watch the library fill up as tasks go by.

Notice a design choice that’s easy to miss. Every task starts again from the same plain base harness, ℋ0. Harness² does not hand the last task’s finely tuned harness to the next one. Old parts can be borrowed, but only when the editor chooses to reuse or adapt them. What carries forward automatically is know-how.

Does the notebook really help? The authors tested it directly. If the editor rewrites the base harness with no runs to compare and no library, scores fall: coding dropped from 73.4 to 63.2 and web tasks from 69.9 to 65.0. Give that same editor a library collected at k = 1 and scores recover to where they started. Give it a library collected with more exploration, at k = 5, and it improves on the base by 0.9, 4.4 and 5.1 points on coding, web and office tasks, without running a single probe. Exploring more on earlier tasks makes later improvement better.

Lessons even cross benchmarks. A library built on JobBench raised one-step results on WorkBuddy-Bench by 0.6, 0.5 and 2.9 points across its three domains.

Does it work?

The authors tested three benchmarks from different kinds of professional work: WorkBuddy-Bench for office-style deliverables across code, web and office documents; JobBench for long, end-to-end job tasks; and LAB, Harvey’s legal-work benchmark. The agents were two models, Gemini 3.5 Flash and GLM-5, each running inside two popular open-source harnesses, OpenCode and Codex. Claude Opus 4.8 served as the default editor. Every number is an average of three runs with tasks in shuffled order, and the library started empty each time.

Choose a benchmark and a setup. Each dot is one method; the faint line shows its distance from the base harness.

A single improvement step raised scores on every benchmark in all four setups, by up to 11.5 points on WorkBuddy-Bench, 4.5 on JobBench and 11.8 percentage points on LAB. Parallel recursion at k = 5 then added roughly 3 to 4 more points on the first two, and 2.6 to 6.7 on LAB.

Two patterns stand out. First, the weaker model often gained more: on WorkBuddy-Bench, GLM-5 with an improved harness overtook Gemini 3.5 Flash running on its untouched one. A better harness can be worth more than a better model. Second, not every rival held up. ReasoningBank, which retrieves past strategies instead of editing the harness, fell as much as 6.6 points below the base on coding tasks, and Harness Scaling finished under the base in seven of twelve comparisons.

Cost matters too. Counting every token spent before handing in the answer, including the improvement work itself, both Harness² settings tested sat on the best-value frontier. Meta-Harness used more compute than Harness² at k = 5 and scored lower.

Which pieces matter

To check that every part earns its keep, the authors removed one at a time, using Gemini 3.5 Flash in OpenCode with a single step. Without the library, nothing learned on earlier tasks is available. With generic editors, two all-purpose editors replace the “general habits” and “domain knowledge” specialists. Without composition, the system simply keeps whichever candidate looked better instead of merging the good parts.

One task, up close

On one JobBench task, Gemini 3.5 Flash had to produce a memo from a stack of planning files. Its first attempt scored 43.1. Reading the trajectory showed the agent didn’t lack knowledge; it lacked process. It never reconciled numbers across the source files, and it never reopened what it had written to check it.

The general-habits edit added a guardrail to list every input, trace each figure to its source, and run a verification script that reopens the finished files. The domain edit added a skill for reconciling schedule, venue, labor and budget files, plus tool tips for awkward number formats. The composer kept all four changes. Toggle to compare.

No stronger teacher required

A fair worry: maybe the gains come from a powerful editor coaching a weaker worker. To test that, the authors let each model edit its own harness, with a budget of k = 2 in OpenCode.

All five models tried, from GLM-5 up to Claude Opus 5, improved on every benchmark. Opus 5 gained 3.3, 5.5 and 3.0 points on WorkBuddy-Bench, JobBench and LAB. GLM-5 gained 13.7 points on LAB. The method works by structure and evidence, not by borrowing a smarter model’s judgment.

What to keep in mind

Evidence is not proof. Behavioral contrasts are noisy, and the star on an adopted harness means “chosen,” not “verified best.” The authors say this plainly.

It costs extra runs. Every step reruns the task several times. Parallel sessions can run side by side, but how long you wait depends on how much you can run at once and how long each run takes.

Not a clean sweep. On LAB with Gemini under Codex, Meta-Harness beat a single Harness² step. And recursion doesn’t always close the gap between starting harnesses: for GLM-5 on WorkBuddy-Bench, the gap between OpenCode and Codex grew slightly.

Transfer is real but modest. Lessons moved from one benchmark to another, adding between half a point and about three points.

The takeaway

Harness² treats improvement as a skill in its own right. Inside each task, it makes careful, side-by-side experiments on its own setup and keeps only what the evidence supports. Across tasks, it keeps a notebook of what worked and why, so the experiments themselves get sharper. The result is an agent that adapts to work it has never seen, without an answer key and without retraining the model.
