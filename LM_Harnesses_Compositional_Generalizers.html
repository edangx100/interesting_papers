Harnesses & compositional generalization

Language model harnesses can be compositional generalizers

Rather than teach an AI model to read ever-longer prompts, teach it to break big, unfamiliar jobs into small, familiar ones. Trained only on short tasks, it then handles tasks up to 64× longer.

An explainer of the paper by Alex L. Zhang, Souradip Chakraborty & Omar Khattab · MIT CSAIL · 2026

The short version

AI models are getting good at small tasks, but they still stumble on long ones: give a model ten times more reading than it practiced on and it starts to get lost. The usual fix is more training on long tasks, which is slow and expensive. This paper tries something different. It wraps the model in a harness, a small program around the model, that lets the model split a big job into many small pieces. Each piece looks like something the model already knows how to do. The authors find that a model trained this way on short tasks keeps working on much longer ones, and on tasks from subjects it never saw. They also show you can train the "planner" part cheaply, using made-up practice worlds.

Below, we build the idea up one picture at a time.

1 · The problem

One prompt that keeps on growing

Most AI agents today work like a diary. Every step (what the model thought, what it ran, what came back) is added to the end of one long prompt. The whole diary is then fed back to the model so it can choose the next step. The paper calls this "trajectory as a prompt". It is how the classic ReAct design works.

The catch: if the model only practiced on short diaries, a long one is something it has never seen. Its performance drifts as the prompt grows. People call this context rot.

Now compare a harness like the Recursive Language Model (RLM). The long input sits outside the model, like a file on disk. The root model writes a short program that cuts the input into chunks and sends each chunk to a fresh helper model. When the task gets longer, the program stays about the same. It just sends out more chunks.

2 · The toolkit

Three ways to control what the model sees

The paper treats the model as a kind of probabilistic function: put text in, get text out, and it is reliable as long as the input looks familiar. Seen that way, a harness's job is to arrange the inputs so that every call gets something it can handle. Popular coding agents already use three tools for this, and they combine well:

Context offloading

The giant input stays outside the model, in the environment. The model only pulls in the slices it asks for.

Programmatic tool calling

Tools are functions inside code. Bulky in-between results live in variables, and only what the program prints comes back to the model.

Sub-agent calling

The model can launch other model calls, each with its own fresh, short context, and collect their answers.

The paper compares four setups that use more and more of these tools:

  • Base model: no harness at all. The whole input goes straight into the prompt.
  • Pi: a ReAct-style coding agent with a terminal, sub-agents, and the input stored as a file.
  • LM + REPL (a CodeAct-style harness): the model writes code over the offloaded input, but it cannot call sub-models from code.
  • RLM: offloading, plus code, plus sub-model calls from inside that code. It uses all three tools.

3 · The key idea

A task can be new while every piece is familiar

Picture a cook who has only ever made soup for four. Ask for soup for four hundred and they don't need a new skill. They need a plan: split the work into pots, have each pot made the usual way, then combine. The whole job is new, but no single step is.

The paper's claim is that a good harness can do this for a language model. The overall task may be unlike anything in training, but if the harness cuts it up the right way, every individual call to the model is something it already handles well.

Locally in-distribution (LID)

"In-distribution" means "looks like what the model was trained on". A harness run is locally in-distribution when each single model call sees a familiar, solvable input, even though the full task is out of distribution. That doesn't require the model to have seen that exact input; it only has to be the kind of thing the model handles reliably.

Two kinds of familiarity work together here:

  1. The root model's plan ("split, ask about each piece, count up") is something it learned in training.
  2. The helper calls do jobs the model could already do before any training, such as "what kind of question is this?"

Training only has to teach the first one. The second comes free.

4 · Test one

Train on short tasks, test on long ones

The authors took six long-reading tasks where length can be dialed up and down. They trained a model (Qwen3-30B-A3B) with reinforcement learning on the short versions only, then tested it on versions 2 to 64 times longer.

What happened. The plain model did very well on the short training tasks, often better than any harness. But that skill didn't carry over to the long versions. The RLM learned more slowly on the short tasks, but its test score on the long tasks tracked its training score: whatever it learned on short tasks, it kept on long ones. Among the harnesses, the RLM did best overall, because it can fan sub-calls out over the offloaded input.

Why: the program doesn't change, it just runs more

Here's an actual pattern from the paper's appendix, simplified. The task (OOLONG) is to look through a big pile of trivia questions and count how many are of each type. At training time the root model wrote a program like this:

# input lives in a variable, not the prompt
questions = extract_questions(context)
batches   = chunk(questions, size=20)
prompts   = [ask(b) for b in batches]
# fan out to helper models
labels    = llm_query_batched(prompts)
answer    = Counter(flatten(labels))

On the 8× longer test task, it wrote essentially the same program. The only thing that changed was how many batches went out.

That only works if the helpers keep doing their small jobs well on the bigger task. The authors checked: on OOLONG, helper calls labeled single questions correctly 85.6% of the time on training tasks and 83.7% on the 8× longer test tasks. The small job stays the same size, so it stays easy.

Where a short piece of code can solve the whole thing (MRCRv2, GraphWalks), the code-only LM + REPL harness also generalizes well. Where you have to actually read and judge lots of pieces (OOLONG, OOLONG-Pairs), you need sub-model calls, and that's where the RLM stands out.

5 · Test two

Same shape, different subject

Length is only one way a task can be new. A task can also be about something completely different but have the same shape of solution. The paper calls carrying a plan across subjects strategy generalization. They trained on one subject and tested on another that shares no content, only structure.

6 · Checking the story

Is the model really reusing what it learned?

To check, the authors compared the root model's moves on each long test task with its moves on the training tasks. They used a word-overlap score, called weighted Jaccard similarity, where 1 means identical and 0 means nothing in common. A high score means the model is replaying a plan it already practiced.

The base model's runs barely overlap with training (0.03–0.22), which makes sense: its "moves" are just the giant prompt, and that changes completely with length. Harnesses that keep the input outside the model reuse their plans.

Reuse alone isn't enough, though. Pi copies its training plan closely on OOLONG (0.87) and still does badly. Its plan doesn't scale: it learned to read a fixed handful of chunks, or to write long lists out by hand, which works at short lengths and breaks at long ones. You need both pieces: a reusable plan and small helper jobs that stay reliable.

7 · A catch

Practice can also teach the wrong habits

Next, the authors asked whether skills learned on those short practice tasks carry over to eight much harder real-world benchmarks that don't share their structure. Mostly, not much. Reinforcement learning on the short tasks raised a weaker model's average by about 7 points but a stronger model's (Qwen3.8-27B) by only 2.4. What each model picked up depended on where it started: the weaker one learned to lean on code and call helpers less, while the stronger one learned to fan out to helpers more.

On messy real tasks, there often isn't a neat, easier version to practice on. That leads to the paper's most practical idea.

8 · The practical trick

Surrogate training: rehearse in a cheap fake world

If what transfers is the root model's plan, you don't need the real task to train it. You need a practice world where the same plan wins. The helper calls in that world can even be fake, returning pre-written answers. The root model's behavior is what's being trained, so the helpers just need to answer.

That's surrogate harness training. For each benchmark, the authors had a strong coding agent (Claude Opus 5.5 in Claude Code) study a separate public split of the task and some example runs. It proposed a plan that should work, then built synthetic practice tasks with different content that the same plan solves. They collected 8,015 successful practice runs and fine-tuned Qwen3.8-27B on them. The result is RLM-27B.

The result

Using the same RLM harness, RLM-27B beat the untrained Qwen3.8-27B on seven of the eight hard benchmarks. Its average rose from 46.1 to 58.5, a 26.9% relative gain.

Counting every token, root and helpers together, RLM-27B used about half as many as the untrained model. Training directly with reinforcement learning on the same synthetic worlds, without the hinted plans, also helped (+6.8 points on average), but didn't produce the efficiency gains.

9 · Going one level up

Harnesses inside harnesses

If one harness run can be treated like a single model call, then a harness can call itself. That lets the newly learned plans be chained together too.

To test this, the authors picked 87 tasks that RLM-27B solves reliably and chained four of them: answer task A to unlock task B, B to unlock C, and so on. By default, the model solves all four inside one growing run. That's the old diary problem again, one level up. With tail recursion, it solves A, then hands B–D to a fresh copy of the harness, which solves B and hands off C–D, and so on. Each task gets a clean slate.

Just telling the model to hand off actually made things worse (55.2% → 47.2%). But teaching it to hand off, with the same cheap surrogate training, raised full-chain success to 77.5%. The skill of splitting a job applies one level up, too.

10 · What to take away

The big picture

  1. Generalize through structure. Don't rely on the network alone to stretch to new inputs. Let a program break new tasks into pieces the model already handles.
  2. Keep every call familiar. The goal is a harness where each single model call is "locally in-distribution", even when the whole task isn't.
  3. Train the planner, not the whole run. Because helper calls compose with skills the model already has, you can target just the root model's behavior, and do it in cheap synthetic worlds with fake helpers.
  4. It nests. A harness can call itself, so learned plans become building blocks for bigger plans.
  5. Not automatic. Plain reinforcement learning can teach habits that don't scale, and a reused plan only helps if the plan itself is sound.

Glossary
Harness
The program wrapped around a language model that decides what it sees, what tools it can use, and how its outputs are acted on.
Compositional generalization
Solving a new problem by combining pieces you already know how to solve.
Trajectory as a prompt
Agent designs (like ReAct) that feed the full, ever-growing history back to the model at every step.
Root model / sub-call
The root model plans and writes code; sub-calls are fresh model calls launched from that code to handle small pieces.
Token
A chunk of text, roughly ¾ of a word. "128K tokens" is about a long novel.
Reinforcement learning (RL)
Training by trial and reward: the model tries, gets scored, and shifts toward what scored well.
Supervised fine-tuning (SFT)
Training by imitation on example runs. RLM-27B was trained this way on synthetic runs.
