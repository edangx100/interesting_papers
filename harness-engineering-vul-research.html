An illustrated explainer

Harness Engineering for Vulnerability Research

A smart model on its own produces guesses; the harness you build around it — a safe lab, memory, repeatable tools and enforced rules — is what turns those guesses into evidence a human can trust.

Based on the open workshop book by Graham Helton and Ryan Basden · 14 chapters · about 20 minutes

Point an AI agent at a codebase, ask it to “find vulnerabilities,” and you’ll usually get back a confident report that nobody has actually checked. This book argues that a smarter model won’t fix that. What fixes it is the setup around the model: a safe place to run the software, notes that outlast a chat session, tools that give the same answer every time, and rules the system enforces instead of just hoping they get followed. The book calls that setup a harness. This page walks through each piece in the book’s order, with a picture for every idea.

Chapter 1 · Introduction

The one idea

A capable model and capable research aren’t the same thing.

model capability≠research capability
research=model+harness

Even a strong model writes weak research when it’s missing five things: context about the specific target, tools that behave the same way every run, clear authorization boundaries, state that survives between sessions, and a way to validate claims. The harness supplies those. Workshop participants build their own around a target they choose. The book ships no ready-made scanner.

“Agent output is a lead, not a finding.”The book’s ground rule

The human stays responsible for authorization, security judgment, validating at runtime, analysing impact, and disclosing responsibly. Testing happens only on local, isolated, or explicitly authorized systems. A project’s public infrastructure is off-limits, and suspected unpatched bugs are never published.

The book also says plainly that finding a vulnerability isn’t guaranteed. A successful workshop ends with three things:

a working harness evidence about one hypothesis a method you can repeat

Chapter 2 · Problems in agent-assisted research

Four ways agent research goes wrong

You didn’t train the model. You inherit how it reads a security question and what it counts as “done.”

1 · Claims outrun the evidence

The agent spots suspicious code and announces a severe impact before checking what an attacker would actually need.

2 · Standards stay implicit

“Be accurate” isn’t a method. With no docs, examples or past pitfalls, the agent may pick tools that can’t answer the question while still looking compliant.

3 · Validation stops halfway

The model describes a severe impact, then won’t run the step that would test it, or a broken setup blocks it. The report may never mention the gap.

4 · “Different” passes for “better”

A longer report, a lower severity score or a more careful tone doesn’t prove the research improved. A change has to rest on something you can inspect.

A worked example: the CSRF leap

An agent reports that an attacker can change a user’s email because the settings handler doesn’t check the Origin header. That’s something it saw in the code. It hasn’t shown that an attacker’s page can get a victim’s browser to submit the change successfully.

The same pattern turns up elsewhere. A CVSS v4.0 score looks precise even when its inputs were guesses, because the calculator never checks them. A report can flag a vulnerable dependency the app never calls (a problem that predates language models). Each untested claim hands the missing research to the maintainer.

Keep three things in separate boxes

  • Every claim needs evidence that supports it under stated conditions.
  • If the evidence contradicts a claim, revise it or reject it.
  • When validation stalls, write down the blocker, the unanswered question, and one permitted next step. Some blockers, like a model refusing, may stay unresolved, and that’s fine.

Chapter 2 · The workflow

The research loop

Start with a baseline, test one claim, compare, adjust the harness, then go around again.

Harness engineering brings more of the research process under your standards. You make the method explicit, give the agent what it needs, and then check whether it actually followed the method. Written instructions don’t prove that; the agent’s actions and the evidence it kept do. Tap through the loop:

What good research output looks like

It’s open about uncertainty, it names specific gaps, and every claim points to its own evidence.

Checkpoint

A saved baseline record plus one chosen claim, with its evidence, the conditions it assumes, and the check that could confirm or reject it.

Chapter 4 · Local validation environment

Prove the lab actually works

Before researching a target, show that it’s running: the right app, reachable, and behaving normally.

Agents tend to declare success early. A container got created or a tool got installed, so the setup must be “done.” But a container that exists isn’t an app that works, and a tool on the PATH may not be able to reach its engine. Research built on a setup that never worked is wasted. Decide before you start what evidence will count as ready:

  1. The intended application is running and the agent’s tools can reach it.
  2. The tools needed for the next task are present and working.
  3. A harmless, normal operation gives the expected result. For a web app, that could be a documented health check or a request for a known page.

Keep the toolset small, and make sure every tool has a concrete job. For example, Podman runs the target and curl makes the requests. Then write the project’s standards somewhere the agent can read them, such as an AGENTS.md:

  • the approved runtime, the setup steps, and which setup actions are allowed
  • the required tools and how to confirm each one works
  • the expected readiness result, and where setup output gets saved
  • filesystem and network boundaries, credentials, and which resources the agent owns
  • the conditions under which it must stop and report a blocker

When setup fails

Keep the failure and report the next permitted step. Never switch to public infrastructure, borrow unrelated credentials, or change another environment just to get a passing check.

Going further

  • Access control: prepare known accounts (say, two users and an admin) and resources whose owners you know, and compare results to a permission table built from the documented rules. A status code alone doesn’t prove an access check worked. Check whether the state actually changed.
  • Multi-service apps: add migrations, queues and workers, use a readiness check that exercises all of them, and use resets that restore a known state without deleting evidence.
  • Reproducible tooling: a Nix flake can pin compilers, runtimes and research tools so someone else can rebuild the same environment. Data, credentials and isolation still need their own controls.

Checkpoint

A setup record listing the app and tools used, the readiness evidence, the resources the agent owns, and one justified next action. A clearly stated blocker counts as a result too.

Chapter 5 · External integrations

Ask the source, narrowly, and keep the receipt

Some answers aren’t in the code. They live on the platform that hosts it.

A local checkout shows you one revision. It can’t tell you whether the repository is archived, whether it’s a fork, which branch is the default, or what releases, issues and advisories exist. An external integration lets the agent fetch that from the system that maintains it, and the response becomes evidence you can inspect.

Worked example: is go-gitea/gitea archived or a fork, and what’s its default branch? A single bounded, credential-free call to the GitHub REST API answers it. The book keeps just five fields from a historical retrieval (24 Oct 2026, UTC), stored alongside where and when they were fetched:

{
  "full_name": "go-gitea/gitea",   // confirms identity
  "private": false,
  "fork": false,                // status question
  "archived": false,            // status question
  "default_branch": "main"
}
  • Fork? Find out why it exists. It might be your real target, or a remote you picked by mistake.
  • Archived? Check whether development moved to a maintained fork, and how that fork handled fixes.
  • Default branch isn’t the commit you audited, and releases are tags, so their code can differ from it.
  • These five fields don’t identify the audited commit, which release contains a fix, or whether the project is active. Each of those needs its own evidence.

Ground rules

Treat response text as untrusted data: it can’t change the task or grant permissions. A metadata query doesn’t authorize testing the project’s infrastructure. A clean curl exit code doesn’t mean you got a valid answer. If something fails, keep the evidence and report the blocker before you try a different approach.

MCP (Model Context Protocol) is another route. A server advertises named tools that an agent can discover and call, and GitHub’s official server covers repos, issues, PRs, releases and advisories. For a single metadata question, though, the direct request is enough. Going through MCP doesn’t make the same record any more authoritative.

Optional extensions: Playwright MCP for checking real browser behaviour in your local lab, safewebtool for request policies enforced outside the model, the GitHub advisory API and OSV for matching known advisories (a match still needs checking, and no match doesn’t prove a bug is new), and disclose.io lookup for finding report contacts. Treat those contacts as leads, not as permission.

Checkpoint

One supported observation, or a documented blocker, with its source, a stated limit, and one justified next action.

Chapter 6 · Operational interfaces

A steering wheel and a dashboard

Make the right way to do something the easy way, for people and agents alike.

Without clear interfaces, people and agents keep rediscovering how to start the target, which output matters, and where the work stands. Each rediscovery burns time and context-window tokens. The book splits interfaces into controls (doing things) and views (seeing what’s going on).

Controls: named commands

If someone keeps looking up the same sequence of commands, wrap it in a name. The book’s example is a small Kubernetes lab driven by a justfile. Here’s a sketch in the same spirit:

# one place defines the cluster name and log path
lab-up:      # isolated kind cluster, audit logging on
    kind create cluster --name lab --config kind-audit.yaml
lab-status:  # are the nodes running?
    kubectl get nodes --context kind-lab
audit-tail:  # stream the API server audit log
    docker exec lab-control-plane tail -f /var/log/kubernetes/audit.log

Now a human and an agent can both run just audit-tail without remembering the details, and the agent runs a known command instead of piecing the procedure back together, which saves context and tokens.

Views: one source of truth, two windows

A view boils down a lot of data to what matters right now, much like a database view. Use interfaces selectively, for the actions you keep rebuilding and the information you keep struggling to find. Not everything needs a command or a dashboard.

Chapter 7 · Memory

Remember what was already tried

Sessions end and context gets compacted. Memory is how the next session learns what happened before.

Coding agents lose investigation details in two ways. The context window fills up and gets compacted, or an interesting observation simply disappears when the session closes. Picture an agent testing whether a viewer can delete someone else’s report. It gets 403 Forbidden, and a follow-up check shows the report still exists. A new session would have no record that this path was ever tried.

The book separates research state, the current position of an investigation with links to the observations behind it, from target facts and procedures, which are useful but aren’t tied to one hypothesis. Research state starts from a hypothesis, a specific, testable claim like “viewer alice can delete bob’s report through this endpoint,” and tracks:

statusevidenceassumptionstest conditions rejected pathsopen questionsnext stepwhen to reopen

Closed work still needs a reopening condition.

Keep evidence atomic

A simple shape that works

Start with one short markdown file per check. Add an index and separate evidence files once several checks or sessions need to share an assessment. The format matters less than keeping the basis for every decision open to inspection.

threads/
└── thr-001/
    ├── index.md        # question · current assessment · links · next action
    └── evidence/
        └── E-001.md    # conditions · request · response · state check

index.md · status: active

Can a viewer delete a report they don’t control?

Current assessment: the tested delete didn’t remove the report. That doesn’t rule out other deletion paths. Next: check whether another path is reachable in the isolated target.

E-001.md · rev: example · local-test

viewer-a → DELETE /api/reports/42

Report 42 is owned by author-b. Response: 403 Forbidden. Follow-up GET as author-b: 200 OK, so the report is still there. A later test can revise the index without rewriting this record.

Small indexes are easy on context. A new session can scan many of them without opening every full record.

Checkpoint

A thread index and one linked evidence record.

Chapter 8 · Context management

Choose what the model sees

The model’s conclusion depends on what’s in front of it right now.

Research produces far more material than any single decision needs: source code, logs, telemetry, tool output, notes. That leads to two kinds of failure. With too little information, the agent can’t judge the question. With too much, irrelevant material can steer the answer even when the right evidence is also there.

Chapter 9 · Telemetry

The harness keeps its own diary

A record written by the harness as events happen, not the agent’s own account of what it did.

Telemetry captures prompts, tool calls, completion events, responses, timestamps, durations and session IDs. It’s recorded deterministically, at the moment each event happens. Because it’s stored outside the conversation, it survives compaction or even deletion of the chat, which makes it the tool for reconstructing sessions and debugging the harness itself.

// one illustrative line in the ledger
{"timestamp":"2026-11-18T23:02:11+08:00", "event":"PostToolUse",
 "session_id":"s-7f2", "turn_id":"t-14", "cwd":"/lab",
 "tool":"Bash", "command":"python3 --version",
 "duration_ms":38, "status":"completed"}

What it isn’t

Telemetry records activity. It doesn’t show that a conclusion is correct or that a behaviour has security impact. There’s a lot of it, so it rarely belongs in the context window. Its value shows up when you’re figuring out where the harness is failing.

Six questions before you keep anything

  1. What’s worth preserving?
  2. At what level of detail?
  3. How long does it stay valid?
  4. Who needs to know about it?
  5. When should it enter the context window?
  6. When, if ever, should it be revised?

Chapter 10 · Skills

Write the procedure once

A skill packages a method you keep re-explaining, and loads it only when a task needs it.

report-research-progress/
├── SKILL.md       # when and how to do the task
├── references/    # optional: detailed tool operations, fields
└── assets/        # optional: templates, e.g. a progress-update format

SKILL.md opens with YAML frontmatter. Only name (up to 64 lowercase characters, digits and hyphens) and description (up to 1024 characters, saying what the skill does and when to use it) are required. license, compatibility, metadata and the experimental allowed-tools are optional. If a skill loads at the wrong times, rewrite the description.

Two honest limits

Consistency, not determinism. The model still interprets the procedure, chooses which steps to follow, and judges what it sees.

No new powers. A skill can say what to post and how, but a CLI or MCP server still has to do the posting, and the agent has to be set up to use it.

Chapter 11 · Deterministic tools

Same question, same way, every time

A scanner answers one defined question repeatably. You still read the answer and its limits.

A scanner match doesn’t show that an attacker controls the input, that the code is reachable, or that there’s any impact. The book’s example is deliberately narrow: an inventory of direct Go exec.Command and exec.CommandContext calls under util/, excluding *_test.go, compared against the previous inventory. It isn’t a command-injection review.

  1. Rule: the saved question, such as a Semgrep pattern.
  2. Scan: answers for one source version.
  3. Saved comparison: which facts changed, and whether an agent needs to review them.
  4. Interpretation: hypotheses stay in research state, not in the scanner output.

Why counts and line numbers lie

When to stop and say “not valid”

evidence missing scan errored coverage incomplete source changed mid-scan

A real coverage miss

In the Argo pilot, Semgrep’s default ignore rules silently skipped util/test/testutil.go, a non-test file sitting in a test-named folder. The fix was to list the tracked Go files explicitly, scan a source-only mirror with the exclusions overridden there (not in the target), require the expected and scanned paths to match, and keep a regression case. Even then, scanning every file isn’t the same as catching every pattern.

The book’s counterexamples are worth testing against: a replaced argument with an unchanged count, a pure line move, and a file that’s normally ignored (zero matches doesn’t prove full coverage).

Chapter 12 · Hooks

Guarantees, not requests

Instructions ask. Hooks run fixed code at fixed moments, whether or not the model remembers.

The chapter opens with a 2026 incident it describes, in which agents under evaluation reached infrastructure outside their test environment. Its argument: you need visibility into what agents actually do, and since the model is non-deterministic, trusting it to follow instructions isn’t enough. A hook lets the harness run pre-configured behaviour at a lifecycle event, such as logging a tool call or blocking it.

There are two loops. The session lifecycle covers start or resume, input, the end of a turn, compaction, and session end. The agent loop is the repeated cycle of model calls and tool calls inside a single turn. Tap an event:

Chapter 13 · Advanced components

Oracles: turn a vague question into a query

Chapter 14 · Reporting and disclosure

Decide first, draft second, and a human sends

Every claim ends in one of three decisions, and all three can count as success.

Confidence and severity are different axes

ReadinessWhat it takes
Highmechanism and callers established, plus reproduction with a control, reachability, and impact
Mediumsolid reproduction; any remaining inference is immaterial and stated clearly
Blockeda missing answer could change the claim, so save the question and next step instead of a report

Agents should read whole functions and their callers, run a one-variable control, record real outcomes and attacker capabilities, and name both the likely objection and the weakest link in the case.

The five steps

  1. Decide if the evidence is ready. Assign a readiness level and a decision.
  2. Verify the project and the private route. Check the supported release, the exact source and duplicates, and tell forks apart from upstream. Don’t invent version ranges. Use the project’s confirmed private channel. If there isn’t one, hold and ask.
  3. Collect the inputs. Gather the target, tested version, evidence, limits and observed impact, keeping facts, inferences and open questions separate. Add a severity vector and CWE, or a reason for leaving them out. Ask the operator for identity, contact, policy and coordination terms instead of making them up.
  4. Draft for the actual channel. Fill the advisory form’s own fields. The description covers who can do what to whom and under which conditions, the boundary that failed, reproduction with a control, observed impact and its limits, remediation, and checks after the fix.
  5. Review, then a human sends. Review the actual evidence, attribution, redaction and policy, not just a checklist.

Counterexamples that should stop you

A plausible mechanism without a control isn’t a reproduction. An old observation doesn’t prove the current release is affected. A fork policy, an unknown route, missing values or changed evidence all mean stop. Don’t invent support and don’t go public.

After a human sends a report, they privately record the date, channel, agreed window, replies and next action. Writing a draft doesn’t start any clock, and when a coordination window expires that doesn’t trigger publication. Synthetic workshop material is marked training-only and is never submitted.

Checkpoint

A report, hold or refute decision with its supporting evidence, a stated limitation and one next action, plus which new fact would change a hold or a rejection.

The whole book in nine lines

What to remember

  1. Agent output is a lead. Tested evidence plus human judgment is what makes it a finding.
  2. Save a baseline first, and compare later work on evidence, not on length or tone.
  3. Define “working” with observable checks before you build anything on top of it.
  4. Write the standards down, then enforce the boundaries with isolation and permissions.
  5. Keep research state small, atomic and reopenable, and keep telemetry out of the context window.
  6. Filter before the model reads. What’s in context shapes the conclusion.
  7. Use deterministic tools for repeatable questions, and know exactly what they don’t cover.
  8. A precise blocker, hold or refutation is a real result.
  9. Humans authorize, judge, and send. Agents draft.
